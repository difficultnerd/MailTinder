# Spec Audit: Consistency, Reasonableness and ASVS 5.0 Level 2

Status: James answered Q1 to Q4 on 3 October 2026 (below); fixes routed to owners.
Scope: `docs/CONTEXT.md`, `planning-roadmap.md`, `plan-open-questions.md`, the BA stories and brief, `specs/S2` to `S10` (with the S7 OpenAPI file), `security/asvs-l2-register.md`, `change-requests/CR-01` and `CR-01a`, and `research/`. Checked against project memory for James's decisions and against OWASP ASVS 5.0 Level 2 as the register uses it.
Method: read every file in full, cross-checked each decision across every document that restates it, then walked the register chapter by chapter against the design. Nothing in the audited files was edited; fixes are routed to the owning threads.

## Verdict

The product decisions are aligned: region (`us-central1` everywhere, no Sydney residue), staging and sandbox mailboxes, the Gemini versus Jev bake-off, no push or digest, the unsubscribe delay and undo race, and the gamification set all read the same across CONTEXT, S2, S4, S5, S7, S9 and S10.

Two late decisions did not propagate. The **passkey lock** is decided in CONTEXT, S2, S5 and S6, but S7, S9 and S10 still describe OAuth sign-in, and nobody has written down how a session-only key works on stateless Cloud Run. The **DKIM rule for unsubscribes** says three different things in four documents. Both produce code an agent cannot write without guessing, and both carry ASVS findings.

The register covers every Level 1 and Level 2 requirement, but only at section level, and about a dozen Level 2 requirements have no control in any spec (listed in the ASVS section below). The specs are not settled yet: 8 high findings need fixing first, 3 of them decisions only James can make.

Severity: **High** blocks build or leaves an ASVS L2 requirement unmet; **Medium** causes conflicting tests or a weaker control; **Low** is stale text or editorial.

Consequences: H8 is settled (S4, S5, S6 and S2 mark Microsoft as v2); H7 simplifies to one Drive app folder, still with ETag concurrency; H4's Microsoft half moves to v2, but the single-use invite token stays (it is the V6.4.1 activation code for Google too); the Outlook.com sandbox mailbox (T1), `fake-microsoft` and Graph tests move to v2.

## ASVS 5.0 Level 2: coverage check

The register lists all 253 Level 1 and Level 2 requirements across V1 to V17, and its N/A calls for GraphQL, WebSocket, file upload, passwords, out-of-band codes, the OAuth authorisation server, OpenID provider and WebRTC hold. The gaps are requirements whose control is missing or contradicted in the specs:

| Requirement | Gap | Finding |
| --- | --- | --- |

| V6.3.4 consistent pathways | OAuth and passkey sign-in of different strength | H3 |
| V6.4.1, V6.4.4 recovery and activation | Invite has no secret; recovery amplifies a single Google compromise | H3, H4 |
| V6.8.1 identity provider spoofing | Microsoft `email` claim unverified | H4 |

| V7.5.1 re-authentication | Linking mailboxes and passkey changes not covered | M1 |
| V9.1, V9.2 self-contained tokens | Own sealed tokens not treated as tokens | M3 |
| V11.1 crypto inventory | Key hierarchy undefined | H1 |
| V13.2.2, V13.2.4, V13.2.5 | IAM gaps; egress allowlist unenforced | M8, M14 |
| V5.4.1, V5.4.2 downloads | CSV export marked N/A | M11 |
| V14.3.1 client clean-up | No `Clear-Site-Data` | L7 |
| V13.1, V15.1.1, V16.4 and alerting | Belong to S11, not started | M16 |
